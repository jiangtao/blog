# Astro 博客国内多渠道同步 Spec

## Problem Statement

博客内容以 Astro Markdown 保存在仓库中，但同步到微信公众号、知乎和掘金时仍依赖不同工具或人工操作。缺少统一入口会导致正文、图片、标题、摘要、标签和出处逐渐不一致；渠道只生成草稿时也缺少统一、及时、可验证的回执。

用户需要把一篇博客文章作为唯一内容源，一次输入后同步到三个国内渠道。同步到可人工审核的草稿或编辑态即为成功，不要求自动公开发布；无论渠道能力如何，都必须保持文章核心内容一致、保留出处，并立即说明每个渠道的结果和下一步人工动作。

## Solution

提供一个个人 Codex Skill 作为统一入口，并由仓库内可测试的确定性命令负责文章解析、预检、格式准备、内容哈希和标准结果。

Skill 接受文章路径或 slug，默认处理微信、知乎和掘金，也允许指定部分渠道。执行时先把 Astro Markdown 解析为规范化文章，验证图片和元数据，生成一份共享临时文章包，再调用渠道适配器：

- 微信适配器复用现有 `md2wechat` 命令行能力创建微信公众号草稿；内容未变化时复用回执，检测到已知草稿变化但底层无安全更新命令时转人工更新，避免重复草稿。
- 知乎适配器先生成官方编辑器人工交接包；只有用户当前请求明确要求同步并接受可见操作时，才使用现有登录态导入 Markdown、检查图片与出处并保存到可审核编辑态。
- 掘金适配器先生成官方编辑器人工交接包；显式同步时使用现有登录态填充 Markdown、分类、标签、摘要、封面与出处，保存并重新打开草稿验证。

同步默认采用 best-effort：一个渠道失败不会阻止其他渠道。完成后返回机器可读的草稿回执集合，并以中文摘要立即通知用户哪些渠道已生成草稿、哪些需要人工操作、哪些失败以及如何恢复。

## User Stories

1. 作为博客作者，我希望只选择一篇 Astro Markdown 博文，就能启动所有国内渠道同步，以免重复寻找和复制内容。
2. 作为博客作者，我希望可以使用文章路径或 slug 作为输入，以适应从编辑器和命令行发起的不同习惯。
3. 作为博客作者，我希望默认同步微信、知乎和掘金，也能只选择其中一个或两个渠道，以便重试单个平台。
4. 作为博客作者，我希望同步前看到文章标题、摘要、标签、图片、出处和目标渠道的预检结果，以便在写入前发现问题。
5. 作为博客作者，我希望源 Markdown 始终只读，以免渠道格式化反向污染博客原文。
6. 作为博客作者，我希望三个渠道保留相同的核心正文和观点，以免不同平台出现内容漂移。
7. 作为博客作者，我希望平台适配只调整格式、图片和元数据，不擅自改写正文，以保持作者表达一致。
8. 作为博客作者，我希望默认在每个平台文章中保留博客 canonical URL，以明确内容出处并把读者导回主站。
9. 作为博客作者，我希望可以把出处切换为 Jerret Life 微信公众号，以适应特定内容分发策略。
10. 作为博客作者，我希望 Astro 根路径图片能够自动解析到博客公共资源，以免同步工具误报文件缺失。
11. 作为博客作者，我希望 SVG 图片在不修改源文件的情况下生成渠道兼容的临时位图，以适配不支持 SVG 的渠道。
12. 作为博客作者，我希望 Markdown 代码块、表格、链接、引用和列表在各渠道保持可读，以免技术文章失真。
13. 作为博客作者，我希望微信继续使用已经可用的 `md2wechat` 草稿能力，以免重复建设。
14. 作为博客作者，我希望微信草稿写入后执行查回验证，以确认图片、代码块、出处和正文确实存入后台。
15. 作为博客作者，我希望知乎同步使用可见的官方编辑器，以便观察导入过程并在平台限制变化时及时停止。
16. 作为博客作者，我希望掘金同步填充分类、标签、摘要、封面和原文链接，以减少保存草稿后的重复编辑。
17. 作为博客作者，我希望知乎和掘金复用现有浏览器登录态，但不读取或打印 Cookie、密码和本地存储，以保护账号安全。
18. 作为博客作者，我希望同步只创建或更新草稿，不自动公开发布，以保留最终审核权。
19. 作为博客作者，我希望同一文章重复同步时优先更新已知草稿，而不是不断创建重复草稿。
20. 作为博客作者，我希望系统用内容哈希识别文章是否变化，以避免无意义地覆盖未变化草稿。
21. 作为博客作者，我希望一个渠道失败时其他渠道仍继续，以免单个平台故障阻断全部分发。
22. 作为博客作者，我希望每个平台都返回统一状态、草稿入口、远端标识、待审核动作、警告和错误，以便快速处理。
23. 作为博客作者，我希望草稿生成后立即收到清晰通知，以免遗漏需要人工审核的平台。
24. 作为博客作者，我希望失败结果指出认证、图片、格式、网络或编辑器变化等具体原因，以便只重试必要步骤。
25. 作为博客作者，我希望同步状态保存在源文章之外，以免平台标识进入博客正文或 Git 历史。
26. 作为博客作者，我希望所有临时转换产物都可以追踪到一次运行，并且不会覆盖原文，以便排查问题。
27. 作为博客作者，我希望没有可用登录态时仍能生成可人工导入的渠道包，以免完全阻塞内容分发。
28. 作为维护者，我希望新增渠道只实现统一适配器契约，而不修改文章解析核心，以便后续接入海外平台。
29. 作为维护者，我希望规范化文章保留语言字段，但本轮不自动翻译，以便未来增加英文内容而不重构接口。
30. 作为维护者，我希望高风险私有 API 和未鉴权浏览器桥接默认关闭且不作为依赖，以降低维护与账号风险。

## Implementation Decisions

- 统一入口命名为 `sync-blog-channels` Skill；它负责编排和用户交互，确定性文章处理由仓库内命令完成。
- Skill 的核心输入为文章路径或 slug；目标渠道默认全部，可显式选择微信、知乎或掘金。
- 公共动作分为只读预检和显式同步。预检不启动远端写入；同步只到草稿或编辑态，不公开发布。
- 规范化文章包含稳定的源标识、标题、作者、摘要、正文、标签、语言、封面、正文图片、canonical URL、出处策略和内容哈希。
- 内容哈希由规范化正文和影响渠道显示的元数据生成，不包含临时文件路径或运行时间。
- 源 Markdown 只读；平台差异只写入一次性运行目录中的渠道产物。
- Astro 根路径静态资源相对博客公共资源目录解析，其他相对资源相对文章目录解析；不存在或逃逸允许目录的资源阻止对应渠道写入。
- SVG 等不受渠道支持的图片在临时目录转换为兼容位图，并保留源图片与派生图片的映射。
- 出处默认使用博客 canonical URL；允许选择公众号出处。出处作为渠道产物的末尾声明，不回写源 Markdown。
- 统一命令支持 `inspect`、`prepare` 和 `sync` 三个阶段；公共管线负责共享文章包准备，各渠道适配器负责无写入的目标渠道预检和 `sync` 边界，并返回相同结构的草稿回执。
- 微信适配器包装 `md2wechat` 的检查、转换、图片上传和草稿创建，不复制其内部实现；当前固定版本未暴露草稿更新或查回命令，因此已知草稿变化时安全降级人工更新，未证明查回时不得标记 `verified`。
- 知乎和掘金适配器默认返回完整官方编辑器人工交接任务；显式同步时才可使用可见官方编辑器与现有浏览器登录态。禁止读取 Cookie、密码、localStorage 或浏览器 profile 文件。
- 浏览器同步必须在写入前展示目标文章和平台，在保存草稿后读取页面可见状态与 URL 进行验证。
- 浏览器不可用、未登录或编辑器结构变化时，返回 `manual-required`，同时保留可导入的渠道包和明确操作清单。
- Wechatsync 不作为运行时依赖；允许参考其纯本地转换思想，但不得启用其未鉴权扩展 API、桥接服务或平台私有 API 默认路径。
- 多渠道同步采用 best-effort；单个平台失败不取消已完成结果，也不阻止其他平台尝试。
- 同步状态记录在用户本地状态目录，按源标识和渠道保存远端草稿标识、草稿入口、最后内容哈希和更新时间；状态不进入文章源文件。
- 相同内容哈希且远端草稿已验证时返回 `unchanged`；内容变化时优先更新已知草稿，无法安全更新时返回 `manual-required`，禁止静默创建重复草稿。
- 标准状态至少包含 `ready`、`prepared`、`draft-created`、`draft-updated`、`unchanged`、`manual-required`、`failed` 和 `skipped`。
- 草稿回执包含渠道、状态、内容哈希、远端标识、草稿/编辑器入口、是否需要人工审核、下一步动作、警告和结构化错误。
- CLI 与 Skill 输出均不得包含访问令牌、Cookie、Authorization、平台临时密钥或完整错误响应体。
- 完成后始终输出三渠道汇总；成功草稿明确标记“待审核”，部分成功明确列出失败渠道和可重试动作。
- 未来海外平台通过新增适配器接入；未来英文能力使用规范化文章的语言字段和独立内容源，不在本轮做自动翻译。

## Testing Decisions

- 测试只验证公共行为，不断言内部函数、平台私有请求或浏览器选择器。
- 第一测试缝是本地文章处理命令：给定代表性 Astro Markdown，验证规范化文章、canonical URL、出处、图片解析、SVG 派生、内容哈希和源文件只读。
- 第二测试缝是统一同步编排器：在 `md2wechat` 进程和浏览器控制这两个系统边界使用测试替身，验证渠道选择、best-effort、幂等判断、标准草稿回执和即时通知。
- 第三测试缝是渠道级真实草稿冒烟：微信验证草稿查回；知乎和掘金验证可见编辑器中的草稿/编辑态、正文一致性、图片、出处和入口。冒烟测试绝不公开发布。
- 本地单元/集成测试沿用仓库现有 Vitest 风格；命令级测试验证 JSON 输出和退出码，不通过内部模块旁路验证。
- 图片处理复用现有图片解析与 SVG 转换测试的先例；外部系统只在边界模拟，不模拟自有文章解析模块。
- 失败测试覆盖缺图、路径逃逸、无浏览器、未登录、格式准备失败、单平台失败、部分成功、重复内容和状态损坏。
- 安全测试验证输出脱敏、源文件未修改、临时目录隔离、无凭据读取接口以及私有 API 默认不可达。

## Out of Scope

- 自动公开发布、定时发布和无人审核发布。
- 批量迁移或回填全部历史文章。
- 读取或管理浏览器 Cookie、密码、localStorage 和 profile 文件。
- 默认启用知乎、掘金私有 API、ZSE 签名或 Wechatsync 桥接服务。
- 重写文章观点、为不同平台生成差异化正文或自动营销改写。
- 自动翻译、英文站点完整国际化和海外平台适配器。
- 代替用户处理平台账号注册、实名、风控申诉或内容审核。

## Further Notes

- 调研、Spec 和实现 Tickets 保存在本地；GitHub 仅同步可验证实现结果、PR 或具有长期公共价值的讨论。
- 三份固定版本研究报告记录了知乎、掘金和 Wechatsync 的来源、实测与安全边界，是本 Spec 的事实依据。
- 真实草稿冒烟需要用户浏览器已登录对应平台；未登录时实现仍须完成准备包、回执和 `manual-required` 降级验证。

## English Summary

Build a `sync-blog-channels` Codex Skill backed by a deterministic, tested local command. Astro Markdown remains the single source of truth. WeChat reuses md2wechat; Zhihu and Juejin use visible official editors with the user's existing browser session. Synchronization stops at a reviewable draft/editor state, preserves canonical attribution and content consistency, returns immediate structured receipts, and never depends on unsafe bridges or private APIs by default.
